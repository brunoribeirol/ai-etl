# Phase 2 — Application Persistence in Postgres

Migrates AI-ETL's own audit trail (`runs`, `analysis_runs`) from SQLite to a
dedicated Postgres database. Explicitly out of scope: authentication, RLS,
multi-tenancy, object storage, queues, workers — all Phase 3+.

## 1. Previous state

`src/ai_etl/audit/db.py` wrote two things per pipeline run:

- `{log_dir}/{run_id}.json` / `{run_id}_analysis.json` — full state/analysis snapshots.
- `{log_dir}/runs.db` — a SQLite file, created on demand with `CREATE TABLE IF NOT EXISTS`,
  holding two tables:

```sql
CREATE TABLE runs (
    run_id TEXT PRIMARY KEY,
    spec TEXT,
    status TEXT,
    error TEXT,
    rows_loaded INTEGER,
    timestamp TEXT
);

CREATE TABLE analysis_runs (
    run_id TEXT PRIMARY KEY,
    gold_subtasks INTEGER,
    science_subtasks INTEGER,
    input_tokens INTEGER,
    output_tokens INTEGER,
    total_tokens INTEGER,
    timestamp TEXT
);
```

`app.py::_load_history` read straight from that SQLite file for the "Histórico" tab.
`runs/runs.db` is gitignored and no run had ever populated it in this checkout (`runs/`
only contained `.gitkeep`) — confirmed before starting this phase, so there was no
production/dev data to migrate.

## 2. New state

Same two tables, same columns and semantics, now living in a dedicated Postgres
database instead of a SQLite file:

```sql
CREATE TABLE runs (
    run_id VARCHAR PRIMARY KEY,
    spec TEXT NOT NULL,
    status VARCHAR(20) NOT NULL,
    error TEXT,
    rows_loaded INTEGER,
    timestamp TIMESTAMPTZ NOT NULL
);

CREATE TABLE analysis_runs (
    run_id VARCHAR PRIMARY KEY,
    gold_subtasks INTEGER NOT NULL,
    science_subtasks INTEGER NOT NULL,
    input_tokens INTEGER NOT NULL,
    output_tokens INTEGER NOT NULL,
    total_tokens INTEGER NOT NULL,
    timestamp TIMESTAMPTZ NOT NULL
);
```

Differences from the SQLite schema, and why:

- `TEXT` timestamp → `TIMESTAMPTZ`: Postgres has a real temporal type; no reason to
  keep timestamps as ISO strings once off SQLite.
- `TEXT status` → `VARCHAR(20)`: cosmetic; status is one of a small fixed set of values.
- No `analysis_runs.run_id → runs.run_id` foreign key, even though `analysis_runs` is
  always written after `runs` in the real pipeline flow. The original schema had no
  such constraint, and adding one would be a scope creep beyond "equivalent schema" —
  left for a future phase if it's ever wanted.
- `INSERT OR REPLACE` (SQLite) → `INSERT ... ON CONFLICT (run_id) DO UPDATE` (Postgres):
  same overwrite-on-rerun semantics, expressed in the dialect's native upsert.

New modules:

- `src/ai_etl/audit/models.py` — SQLAlchemy Core `Table` definitions (`metadata`, `runs`,
  `analysis_runs`). Core, not the ORM, to match the style already used in
  `sources/postgres_source.py` / `destinations/postgres_dest.py`.
- `src/ai_etl/audit/connection.py` — `get_engine()`, a process-cached SQLAlchemy engine
  built from `APP_DATABASE_URL` (falls back to the docker-compose default locally).
- `alembic/` + `alembic.ini` — migrations. `alembic/env.py` reads `APP_DATABASE_URL` at
  runtime (the same variable the app uses) rather than a hardcoded URL in `alembic.ini`.
  One migration so far: `0001_initial_schema.py`, hand-written to mirror `models.py`
  exactly (not autogenerated, since there was no prior revision to diff against).

`src/ai_etl/audit/db.py` keeps its public API unchanged — `save_run`, `save_analysis`
— and gains `load_history(limit=20)`, used by `app.py`'s "Histórico" tab in place of the
inline `sqlite3` query that used to live there. JSON-file writing is untouched byte for
byte; only the row-insert half of `save_run`/`save_analysis` changed backend.

### `APP_DATABASE_URL` vs. `POSTGRES_URL`

Two logically separate Postgres databases, both defined in `docker-compose.yml`:

| Variable | Purpose | Service | Port |
|---|---|---|---|
| `POSTGRES_URL` | Pipeline source/destination — the user's own data (`sources/postgres_source.py`, `destinations/postgres_dest.py`) | `postgres` | 5432 |
| `APP_DATABASE_URL` | AI-ETL's own audit trail (`runs`, `analysis_runs`) | `app-postgres` | 5434 |

Test variants: `postgres-test` (5433, pre-existing) and `app-postgres-test` (5435, new).
Kept as separate containers (not separate databases in one container) to mirror the
existing `postgres`/`postgres-test` split and keep the two concerns — pipeline data vs.
application data — trivially separable if they ever need different lifecycles, backup
policies, or hosts.

## 3. Data migration decision

None performed. `runs/runs.db` never existed in this checkout (confirmed via
`find . -iname "*.db"` before starting), and the project is pre-release/TCC-stage —
there is no production data anywhere. The Postgres schema starts empty via
`alembic upgrade head`.

## 4. Commands

```bash
# Start the application database (+ its ephemeral test variant)
make app-db-up
make app-db-test-up

# Apply migrations
make db-migrate          # runs `alembic upgrade head` against APP_DATABASE_URL

# Stop it
make app-db-down
```

`.env.example` gained:

```bash
APP_DATABASE_URL=postgresql://ai_etl_app:ai_etl_app@localhost:5434/ai_etl_app_db
```

## 5. Tests added

- `tests/unit/test_audit_db.py` (rewritten): JSON-writing behavior only, with
  `_write_run_row`/`_write_analysis_row` monkeypatched to no-ops — no DB required, same
  as before this phase (they never touched real SQLite disk beyond `tmp_path` either).
- `tests/integration/test_audit_persistence.py` (new): `save_run` insert + upsert-on-conflict,
  `save_analysis` token aggregation, `load_history` ordering, and the soft-fail path when
  the app database is unreachable. Runs against `app-postgres-test` (5435).
- `tests/integration/test_alembic_migration.py` (new): applies `alembic upgrade head` from
  a clean slate and asserts the resulting tables/columns; also checks `downgrade base`
  drops both tables.

Both new integration test modules use `pytest.mark.skipif` gated on a live connection
check, so `make test`/CI stay green on machines without Docker running — no integration
test in this repo depended on a live Postgres container before this phase, so this
establishes that pattern rather than following an existing one.

`tests/unit/test_pipeline_service.py` needed no changes: it already monkeypatches
`save_run`/`save_analysis` at the `pipeline_service` module level and asserts call
order/arguments, never touching the persistence backend.

## 7. Remaining limitations

- No connection retry/backoff around `get_engine()` — a downed `app-postgres` makes
  `save_run`/`save_analysis` raise (matching the "writes should be loud, reads can be
  soft-fail" split already implicit in the original `_load_history` try/except).
- No FK between `analysis_runs.run_id` and `runs.run_id` (see §2) — acceptable since the
  application always writes `runs` before `analysis_runs` in practice, but nothing
  enforces it at the DB level.
- No pagination beyond `load_history(limit=...)`; matches Phase 1's hardcoded `LIMIT 20`.
- Single `0001` migration; no autogenerate workflow documented yet since there's no prior
  revision to diff against — worth revisiting once schema changes start happening in Phase 3+.
