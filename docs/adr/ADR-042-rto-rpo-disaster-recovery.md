# ADR-042: RTO/RPO Targets and Disaster Recovery Posture

**Status:** Accepted
**Date:** 2026-08-27
**Sprint:** Wave 3 (post-audit strategic decisions, `docs/work/2026-08-26-strategic-decisions-execution-plan.md`)

## Context

The 2026-08-22 SOC2 self-assessment (`docs/compliance/soc2-readiness-assessment.md`,
CC7 table) already flagged this as a P1 gap, in its own words: *"No
documented, tested backup/restore procedure. Supabase almost certainly has
point-in-time recovery available on paid tiers, but whether it's enabled, and
whether a restore has ever been rehearsed, is unverified."* No RTO or RPO
figure existed anywhere in the repo before this ADR — grepping the whole
codebase and `docs/` for "RTO"/"RPO"/"disaster recovery" returned nothing.

The later X-PRO.ai gap analysis (`docs/CURRENT_STATE.md`, 2026-08-27 entry)
independently surfaced the same gap and the owner approved writing this ADR as
one of 3 small Wave 3 items.

**Current deployment topology** (confirmed against the repo, not assumed):

| Component | Where | Backup ownership today |
|---|---|---|
| API (FastAPI) | Railway service `ai-etl` | Stateless — no backup needed, redeployed from `main` |
| Celery worker | Railway service `tranquil-appreciation` | Stateless — same as above |
| Celery beat (scheduler) | **Not yet deployed** (`docs/CURRENT_STATE.md`) | N/A — scheduled pipelines don't fire in production today |
| Frontend | Vercel, separate deployment | Stateless, redeployed from `main` |
| Application Postgres (`APP_DATABASE_URL`) | Supabase-managed | Platform-managed, **not independently verified enabled** (this ADR's central gap) |
| Redis (Celery broker + rate limiting) | Railway managed addon | Ephemeral by design — see Decision 3 |
| Run artifacts (Silver/Gold/Science CSVs, figures) | S3 (or local disk in dev) | Regenerable, see Decision 2 |

This asymmetry matters for the decisions below: **only one component in this
whole topology holds data that cannot be regenerated by re-running code** —
the application Postgres database. Everything else is either stateless
(API/worker/frontend, redeployed from Git) or reconstructible from Postgres
plus a pipeline re-run (S3 artifacts, Redis).

## Decision 1 — RTO/RPO targets, sized to this project's actual stage

**RTO (Recovery Time Objective) for a full-service outage: 4 hours.**
**RPO (Recovery Point Objective) for the application Postgres database: 24
hours.**

**Why these numbers, not tighter or looser ones.** This project is
pre-revenue (TCC-stage, no paying tenants yet — confirmed by
`docs/CURRENT_STATE.md`'s own "Clerk dev mode" status), so there is no
existing production SLA, contractual uptime commitment, or measured incident
history to derive a number from — the same honest constraint `ADR-033`'s
error-rate SLO (≤1%) faced and stated explicitly rather than inventing false
precision. 4h RTO / 24h RPO are standard, conservative first targets for a
single-region, single-instance-per-service deployment with no active-active
failover — tight enough to be a real commitment once real tenants exist,
loose enough not to require infrastructure (multi-region failover, continuous
replication) this project's current scale doesn't justify. **Revisit once
real production traffic and a real uptime commitment exist** — this is a
starting target, not a permanent one.

**Explicitly not covered by these targets:** a regional Supabase/Railway
outage affecting the underlying platform itself (out of this project's
control — mitigated only by each platform's own SLA, not by anything this ADR
can add); a compromise requiring the LGPD breach-notification path
(`ADR-025`/tenant deletion service), which is a security-incident response
process, not a DR/backup-restore one, and stays out of scope here.

## Decision 2 — Recovery strategy per component

**Application Postgres (the one genuinely stateful, non-regenerable
component): rely on Supabase's managed point-in-time recovery (PITR), but
treat "enabled and tested" as an open verification, not an assumption.**

Building a second, independent backup pipeline (e.g. a scheduled `pg_dump` to
S3) was considered and rejected for now: Supabase's own managed PITR is the
platform's primary durability mechanism, and duplicating it without first
confirming what's already there would be effort spent before the actual gap
(verification, not mechanism) is closed. **Real, unresolved follow-up, not
silently deferred:** confirm on the actual Supabase project dashboard (1)
which plan tier this project is on and whether PITR is enabled on it, (2)
what retention window that PITR covers, and (3) actually perform one test
restore into a scratch database and time it — none of this requires code, and
none of it has been verified from inside this coding environment (no Supabase
dashboard access here, same class of limitation `ADR-039`'s Vercel Sandbox
credentials gap and `ADR-033`'s Sentry DSN gap already documented honestly
elsewhere in this project). Until that verification happens, this project's
actual current RPO for Postgres **should be treated as unknown, not as the
24h target above** — the target is what this ADR commits to; today's real
number is unverified.

**S3 run artifacts: no independent backup, by design.** Every artifact under
`audit/storage.py` (`{run_id}.json`, `_silver.csv`, `_gold_*.csv`, figures) is
fully regenerable by re-running the same `saved_pipeline` — nothing here is a
system of record (`docs/architecture-storage.md` already establishes this
split explicitly: "independently scaled and independently backed up on
purpose"). S3 itself already provides 11 nines of object durability
(AWS's own published figure) against physical loss, which is a stronger
guarantee than anything this project would add on top. **A lost/corrupted
run's real recovery mechanism is "user re-runs the saved pipeline,"
not a restore** — this is a deliberate, low-cost trade-off given that
artifacts are byproducts of Postgres/pipeline-plan state, not the state
itself.

**Redis: no backup, by design — it is disposable cache/queue state, not a
system of record.** The Celery broker holds in-flight task messages
(re-enqueued or lost is an acceptable outage-recovery cost at this project's
current scale — no financial transaction depends on a specific queued Celery
message surviving a Redis restart) and `services/execution_queue.py`'s rate
limit counters (worst case after a Redis loss: a tenant's rate-limit window
resets early, not a security issue). Losing Redis loses in-flight work, never
committed data.

**Stateless services (API, worker, frontend): redeploy from Git, no restore
procedure needed.** Recovery here is "push the last known-good commit / trigger
a Railway or Vercel redeploy," already the existing normal deploy path — not a
new DR mechanism.

## Decision 3 — What "recovery" actually means for the Silver vs. Agentic BI split

Worth stating explicitly because this project's own architecture makes it
non-obvious: a full outage recovery does **not** require replaying every
historical pipeline run. `saved_pipelines` (the pipeline definitions
themselves — source configs, transformation specs, schedules) is the
Postgres data that must survive; the *historical run outputs* in S3 are
useful history, not required for the product to keep functioning post-
recovery. Once Postgres is restored, every `saved_pipeline` can be re-run on
its next scheduled tick (or manually) to regenerate current-state artifacts —
this is the same "S3 is a cache of derived outputs, Postgres is the source of
truth" split `docs/architecture-storage.md` already documents, just stated
here in DR terms.

## Consequences

- A documented RTO (4h) / RPO (24h) target exists for the first time,
  matching the honesty precedent this project's other ADRs already set
  (`ADR-033`'s SLO section, `ADR-039`'s unverified-in-this-environment
  containment test) — stated as a target derived from the project's actual
  pre-revenue stage, not invented false precision.
- The real, still-open gap is verification, not architecture: whether
  Supabase PITR is actually enabled, its actual retention window, and a real
  timed test restore — none of which this coding environment can perform.
  Tracked as required next-session follow-up (`docs/CURRENT_STATE.md`), same
  as the other credential-gated verification gaps already tracked there
  (Vercel Sandbox live containment test, Sentry DSN).
- No new backup infrastructure was built — the decision was "verify and rely
  on Supabase's existing PITR" over "build a redundant `pg_dump` pipeline,"
  explicitly to avoid effort duplicating a mechanism that likely already
  exists, before confirming what's actually there.
- S3 artifacts and Redis are explicitly *not* backed up, by design, with the
  reasoning recorded here so a future reviewer doesn't mistake the absence
  for an oversight.
